# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A single-file, client-side visualization tool for etymological/lexical trees ("CSV layer graph"). There is no build system, package manager, or test suite — the entire application lives in [index.html](index.html), which loads D3.js and PapaParse from CDNs.

## Running / developing

There is no build step. Open [index.html](index.html) directly in a browser (or serve the directory with any static file server) to run the app. Changes take effect on page reload.

There are no lint or test commands configured for this project.

## Data files

- [multilingual_tree_data.csv](multilingual_tree_data.csv) — a flat etymology dataset (`id, word, parent_id, meaning, category, tags, paradigm_id`) used as source data for the relational model below. Not consumed directly by `index.html`. `paradigm_id` is blank for almost every row; it only groups words that are curated as belonging to the same synchronic paradigm despite having no shared ancestor (see `CONNECTED_TO` below) — e.g. the English "to be" suppletive paradigm (`am/is/are` ← *h₁es-, `was/were` ← *h₂wes-, `be/been` ← *bʰuH-, three distinct PIE roots).
- [relational_database.py](relational_database.py) — a one-off migration script that normalizes `multilingual_tree_data.csv` into a relational schema and writes it to a local SQLite file (`etymology.db`) via pandas. Run with `python relational_database.py` (requires `pandas`). This is exploratory/offline tooling, separate from the browser visualization.
- [export_to_neo4j.py](export_to_neo4j.py) — reads `etymology.db` (run `relational_database.py` first) and writes `graph_export.cypher`, an idempotent (all-`MERGE`) Cypher script for loading the same data into Neo4j as a property graph. `DEVELOPED_INTO` edges are **reified as `:Etymology` nodes** rather than plain relationships — Neo4j relationships can't be the target of another relationship, and a single etymological claim can carry multiple citations (e.g. both Pokorny and LIV citing the same root), so citations need a node to attach to (`(:Etymology)-[:CITED_BY {locus, note}]->(:Source)`). Every other relationship type (`HAS_WORD`, `CONNECTED_TO`, `RESOLVES_INTO`, `HAS_CATEGORY`) stays a plain Neo4j relationship since nothing else needs to attach provenance to them. No Neo4j instance or Python driver is available in this dev environment, so this has been verified by inspecting the generated Cypher, not by an actual import.
- [load_into_kuzu.py](load_into_kuzu.py) — reads `etymology.db` and loads it into [Kuzu](https://kuzudb.com) (`pip install kuzu`), an embedded (file-based, no server/account) graph database with a Cypher-like query language, at `kuzu_db`. This is the **recommended way to query the graph** (richer filtering than Neo4j's free tier, no reification needed): Kuzu supports `LIST<STRUCT<...>>` as a native relationship property type (Neo4j only allows flat scalars/arrays of scalars), so every `DevelopedInto` relationship carries its own `citations` list directly — querying e.g. `WHERE any(c IN rel.citations WHERE c.source_name = 'Pokorny')` or `WHERE size(rel.citations) > 1` works directly on the edge, no `:Etymology` node workaround required. **Gotcha confirmed in this environment:** as of kuzu 0.11.3, `COPY ... FROM <pandas DataFrame>` crashes against pandas 3.0's new default PyArrow-backed string dtype (`RuntimeError: ... KU_UNREACHABLE`) — this script avoids it entirely by using `sqlite3` + parameterized `conn.execute(query, parameters={...})` calls instead of DataFrame scanning. Verified by actually running it and querying the resulting `kuzu_db` (node counts match the relational tables; multi-citation and edge-property-filter queries confirmed working).
- [visualize_graph.py](visualize_graph.py) — reads `kuzu_db` (run `load_into_kuzu.py` first; requires `pyvis`) and writes `graph_visualization.html`, a self-contained interactive node-link diagram (open directly in a browser, no server/account/Docker) using the same accent-color palette as `index.html`. Every node is added up front from its own node-table query (not just discovered via edges), since some nodes have no incoming/outgoing edge at all — e.g. the "Swadesh List" scheme, which tier-2 categories reference only via the `scheme_id` *edge property* (their actual graph edge points at their tier-1 parent category instead), so nothing in the graph structure itself points at the Swadesh scheme node. For the fuller interactive query-and-visualize experience (type arbitrary Cypher, see it rendered live), Kuzu also ships a Docker-based web explorer (`docker run -p 8000:8000 -v <abs path to kuzu_db>:/database kuzudb/explorer:latest`, then open `localhost:8000`) — `visualize_graph.py` is the lighter no-Docker alternative.
- [tables.html](tables.html) — a standalone browser page (PapaParse only, no build step) that lets anyone upload the same flat CSV (or click "Load Sample Dataset") and see the same relational schema rendered as HTML tables, without needing Python/SQLite. `buildRelationalTables()` in this file must be kept logically in sync with `relational_database.py` — they're independent implementations of the same graph-building logic.

### Relational schema (relational_database.py / tables.html)

Eight tables, built from the flat CSV. A guiding principle throughout: provenance/classification metadata (which scheme classifies a category, which source attests to an etymology) lives on the **edge**, not on the node it describes — since the same node can be viewed differently depending on which relationship you're looking at (e.g. a category nested differently under different schemes, or a word's lineage attested differently by different dictionaries).

- **words** — one row per unique CSV `id` (`node_type=WORD`), plus one synthetic row per distinct `tags` value (`node_type=LANGUAGE`).
- **edges** — `relationship_type` is one of: `DEVELOPED_INTO` (word→word lineage, `is_diachronic` flags whether the `tags` value changed; **and** language→language, aggregated from the distinct `(parent_tag, child_tag)` pairs found among diachronic word-level edges — e.g. Latin→Spanish), `HAS_WORD` (language→word; its inverse `TAGGED_AS` is derived, not stored — a SQL `VIEW` in the sqlite output, a comment/note in `tables.html`), `CONNECTED_TO` (words sharing the same non-blank `paradigm_id` — stored once per pair, not twice). `CONNECTED_TO` is **not** derivable from `parent_id`/`tags`: suppletive paradigm members (e.g. "to be") share no common ancestor, so this relation only exists where the CSV explicitly curates it via `paradigm_id`.
- **semantic_schemes** — the classification system a category's hierarchy edge belongs to. Three illustrative schemes exist so `scheme_id` is actually exercised rather than pointing at one row everywhere: "Buck's Schema (approximate)" (tier-1 broad categories), "Swadesh List (approximate)" (tier-2 specific concepts), "Concepticon (approximate)" (the `Grammar` category specifically, since a function-word grouping doesn't fit a semantic-field scheme — illustrating why more than one scheme is useful). None of the three names/assignments are verified against the real published schemes; this is a placeholder pending the professor's confirmation of the exact tagging-scheme/tag entity shape.
- **semantic_categories** — just `category_id` + `label`. Carries no parent or scheme — those live on `category_edges` instead, since the same category could in principle be nested differently under different schemes.
- **category_edges** — the `RESOLVES_INTO` hierarchy between two category nodes (`child_category_id`, `parent_category_id`, `scheme_id`): tier 1 is the broad `category` column value, tier 2 is each root-level concept's `meaning`, parented under its tier-1 category. Tier-1 categories have no parent category, so `parent_category_id` is null and the edge resolves directly into the scheme instead — the scheme acts as the implicit root of its own category tree.
- **word_categories** — many-to-many bridge between `words` and `semantic_categories` (plain membership, no scheme — scheme only applies to the hierarchy edge between two categories, not to word↔category membership).
- **sources** / **citations** — LIV/Pokorny/OED-style citation tracking. A citation attaches to the specific `edges` row it attests to (`citations.edge_id` → `edges.edge_id`, plus `source_id`/`locus`/`note`) rather than to a word in isolation — e.g. an OED citation about *canis* attaches to the `*ḱwón- → canis` `DEVELOPED_INTO` edge specifically, since every non-root word has exactly one incoming lineage edge. Only populated for the built-in sample dataset in `tables.html` (an arbitrary uploaded CSV has no citation data to attach); the sample citations are illustrative, not verified against the physical dictionaries.

## Architecture of index.html

The app expects two CSV inputs (uploaded via file pickers, or generated from the built-in "Load Sample Dataset" button using the `SAMPLE_NODES_CSV`/`SAMPLE_EDGES_CSV` constants):

- **Nodes CSV**: `id, label, layer, layer_name` — `layer` is a numeric rank used to group nodes into horizontal bands (e.g. language family → language → word → gloss).
- **Edges CSV**: `source, target, type, sources` — `sources` is a semicolon-separated list of citation sources (e.g. `LIV`, `Pokorny`, `Consensus`) used for edge coloring/filtering; `type` distinguishes relationship kinds (e.g. `DERIVED_FROM`, `HAS_MEANING`, `BELONGS_TO`).

Data flow: file input change handlers parse CSVs with PapaParse into `rawNodeRows`/`rawEdgeRows` → `tryBuild()` → `buildAndRender()`, which builds the D3 force simulation, layer bands, and adjacency maps, then calls `render()` on every interaction (click/hover/breadcrumb navigation) to recompute visibility and styling without rebuilding the simulation.

Key concepts to understand before modifying rendering logic:

- **Layers as focus depth, not literal 3D**: nodes are laid out per-layer band (`d3.forceY` pinned to `layerBandY`), but `projectTo3D()` fakes a pseudo-3D depth effect by scaling node/edge positions outward or inward based on `layerIndex - focusIndex` (`zScale`). Despite the name, this is a 2D visual effect (see the "back to 2d" commit history), not a WebGL/three.js scene.
- **Focus/drill-down navigation**: `focusIndex` and `activeParentId` track which layer and parent node the user has drilled into; clicking a node re-centers the view, and `renderBreadcrumb()` reflects the current path. `resetAll()` (triggered by clicking empty canvas) clears this state.
- **Word-inspection tree mode**: clicking a word node sets `selectedInspectedNodeId` and calls `computeTreeLayoutPositions()`, which walks `diachronicAncestors`/`diachronicDescendants` maps (built from `DERIVED_FROM` edges) to lay out a 4-lane pedigree tree (ancestors / node / descendants / meanings) at fixed X positions, overriding the force simulation via `node.treeX`/`node.treeY`.
- **Highlighting vs. visibility are separate passes**: `highlight()` (hover) toggles opacity based on the adjacency map; `render()` (click/state changes) recomputes which nodes/edges are structurally visible for the current focus/inspection state. Both run independently on top of the same DOM selection.
- **Source filtering**: `sources` values are normalized via `SOURCE_NORMALIZATION_MAP` (handles typos/case variants like `picorni` → `Pokorny`) before being matched against the `selectedSources` set driven by the sidebar checkboxes.
